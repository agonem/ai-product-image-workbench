# 接口与数据契约草案 v0.1

业务接口仍是 **拟定契约**；T01 仅实现下述健康接口。路径与字段可在首次代码评审时调整，调整须同步 Schema、前后端和测试。所有资源 ID 为服务端生成的 opaque string；时间为带时区 ISO 8601；长度与业务上限待 P0 决定。

## 0. T01 开发环境健康接口

需求：PRD-G06；任务：T01；验收：ACC-T01。两个端点只反映当前 HTTP 进程可响应，不承诺数据库、Worker、AI 或业务就绪。

| 调用方 → 服务 | 方法与路径 | HTTP 200 JSON |
| --- | --- | --- |
| 前端 → Java | `GET /api/v1/health` | `{"status":"UP","service":"business-service","api_version":"v1"}` |
| 开发检查 → Python | `GET /internal/v1/health` | `{"status":"UP","service":"image-service","api_version":"v1"}` |

无输入、无密钥、无素材、无业务状态写入。前端通过 Vite 的 `/api` 开发代理访问 Java，不直连 Python。两服务默认仅绑定 `127.0.0.1`，没有实现认证，不能作为生产部署。前端在连接失败、超时或响应不符合上述字段时显示失败并允许重试。后续业务健康/就绪语义须单独定义；本次不改变任务 Schema。

## 1. 前端 → Java（/api/v1）

| 方法与路径 | 用途 | 要点 |
| --- | --- | --- |
| `POST /assets/uploads` | 获取受限上传凭证或走服务端上传 | project_id、type=PRODUCT/GIFT；回收未完成上传 |
| `POST /assets/{id}/complete` | 校验上传完成并处理元数据 | 校验 MIME 真值/文件大小/像素数/哈希/归属；返回可预览状态 |
| `POST /assets/{id}/cutout` | 发起或取得抠图结果 | alpha 预览与人工确认状态 |
| `GET /templates?type=scene|layout|style` | 已发布模板 | 返回版本、预览与允许参数 |
| `POST /tasks` | 创建独立生成任务 | 必须携带 `Idempotency-Key` 和 `feature_type`；返回 202 |
| `GET /tasks/{id}` | 轮询状态与结果 | 只返回当前授权用户可读的信息 |
| `POST /tasks/{id}/retry` | 针对失败任务重试 | 新 attempt，不能改写原配置快照 |
| `GET /artifacts/{id}/download` | 下载已授权结果 | 代理或短时效签名链接 |
| `POST /admin/templates` 等 | 草稿、测试、发布、停用 | 仅管理员；另行定义管理 API 细节 |

示例 `POST /tasks`：

```json
{
  "project_id": "p_123",
  "feature_type": "GIFT",
  "product_asset_id": "a_product",
  "gift_asset_id": "a_gift",
  "manual_text": "下单赠清洁刷",
  "template_version_id": "tv_layout_1",
  "layout": {"product": {"x": 0.12, "y": 0.11, "width": 0.72, "height": 0.72}, "gift": {"x": 0.70, "y": 0.72, "width": 0.22, "height": 0.22}},
  "output_preset_id": "preset_draft_1"
}
```

坐标是相对画布的 0..1 比例，原点左上；尺寸、旋转和允许越界范围要经 UI/图像引擎统一确认。赠品默认右下是界面初始值，可编辑；`output_preset_id` 在拼多多规格确认前只代表内部预览导出配置。

`SCENE` 专有字段：`scene_template_version_id` 或 `scene_custom_prompt`、可选 `style_custom_prompt`、商品布局；两种场景输入可以有明确组合规则，但不能都为空。`SELLING_POINT` 专有字段：`selling_points`（人工字符串数组）和 `layout_template_version_id`；一条文案一张产物，数量上限待定。三种类型使用 discriminated union 校验，绝不根据缺失字段猜类型。

统一任务响应：

```json
{
  "id": "t_123", "feature_type": "GIFT", "status": "QUEUED",
  "attempt": 1, "created_at": "2026-09-24T00:00:00Z",
  "artifacts": [], "error": null
}
```

失败响应示例：`{"code":"CUTOUT_REVIEW_REQUIRED","message":"请检查商品抠图边缘","correlation_id":"..."}`。最小错误码：`INVALID_ASSET`、`UNAUTHORIZED_ASSET`、`CUTOUT_REVIEW_REQUIRED`、`INVALID_LAYOUT`、`TEXT_OVERFLOW`、`PROVIDER_UNAVAILABLE`、`GENERATION_FAILED`、`OUTPUT_VALIDATION_FAILED`、`TASK_CONFLICT`。内部故障细节与供应商错误不得直接暴露。

## 2. Java → Python Worker

Java 在数据库事务中提交任务与 outbox 记录；发布器投递 `image.task.requested.v1`。Worker 只读取受限的对象引用/临时访问令牌，结果写到任务限定路径，回执 `image.task.completed.v1` 或 `image.task.failed.v1`。不得在消息体存放图片二进制、用户密码或长期密钥。初期若采用 DB 轮询，保留同一请求与回执语义。

请求契约草案见 `contracts/task.schema.json`，含 `schema_version`、`task_id`、`attempt_id`、`feature_type`、输入资产引用及哈希、模板快照和参数、目标路径、关联 ID。成功回执包含产物类型、对象引用、sha256、尺寸、耗时、供应商与模型标识；失败回执包含可重试标记、内部错误码和安全消息。Java 在更新状态前核验 attempt_id 与产物存在性，重复回执幂等处理；旧回执只记录不覆盖。

## 3. 表模型（概念级）

| 表 | 主键与关键字段 | 约束 |
| --- | --- | --- |
| `users` | id、role、status | 最小权限 |
| `projects` | id、owner_id、name | 项目归属 |
| `assets` | id、project_id、kind、object_key、sha256、width、height、review_status | 类型与访问权校验；源图不可被替换 |
| `templates` | id、type、name、published_version_id、state | 模板身份稳定 |
| `template_versions` | id、template_id、version、config_json、created_by、published_at | 一旦发布不可改写 |
| `generation_tasks` | id、project_id、feature_type、status、request_snapshot_json、created_by、created_at | type/状态受限；配置快照 |
| `task_attempts` | id、task_id、attempt_no、status、started_at、ended_at、error_code、provider_info | 唯一(task_id, attempt_no) |
| `artifacts` | id、task_id、attempt_id、kind、object_key、sha256、width、height | 成品不可悄然覆盖 |
| `outbox_events` | id、event_type、payload、published_at | 可恢复发布 |
| `audit_events` | id、actor_id、action、resource_id、timestamp | 记录敏感变更 |

用数据库迁移脚本实现；object_key 不应是公网永久地址。保存期限、清理孤儿产物和删除传播规则尚未决定。

## 4. 版本策略

对外 API `/api/v1`；任务 schema 有独立 `schema_version=1`；模板发布产生不可变版本；Prompt、供应商/模型和原图/alpha 哈希存任务快照。破坏性更改先引入新版本并让前端/Worker 双方通过契约测试，然后滚动发布。建议从契约生成 Java/Python/TypeScript 类型，但生成器是实现选项，不能取代人工审核语义。

## 5. T03：任务契约 v1 与数据库基线

任务 T03；需求 PRD-G03/G06、PRD-S01/S02/S03；约束 PRD-G01/G04；验收 ACC-T03，提供 ACC-07/08/10 的基础约束。

T03 固化数据协议、提供三端离线校验器及 PostgreSQL/Flyway 迁移，不开放任务写入 API，不执行 Worker，不发送 outbox。上文业务 HTTP 路径仍待 T04/T05 实现；已有健康接口保持不变。

### 5.1 规范源与兼容性

`contracts/*.schema.json` 是 Draft 2020-12 规范源；`common.schema.json` 共用结构；前端、Java、Python 使用同一批 `contracts/fixtures/cases.json` 正反样本验收。所有引用仅解析仓库/JAR 内注册的 schema，不按用户输入下载 schema。`https://schemas.product-image-workbench.invalid/v1/` 是离线标识，不是网络服务。

| 文件 | 协议 |
| --- | --- |
| `task-create.schema.json` | `POST /api/v1/tasks` 请求体，按 feature_type 区分三种独立输入 |
| `idempotency-key.schema.json` | 请求头 Idempotency-Key 的语法；可见标识字符 1..128，属于技术协议限制，不是业务配额 |
| `task-response.schema.json` | 对外任务响应；不暴露对象存储 key 或供应商内部错误 |
| `task.schema.json` | `image.task.requested.v1`，保留原草案文件路径 |
| `task-completed.schema.json` | `image.task.completed.v1` |
| `task-failed.schema.json` | `image.task.failed.v1` |

原 `task.schema.json` 是未被运行代码使用的草案。此次首次固化 v1，增加事件标识、必需的 alpha/快照、严格分支及回执，没有既有业务数据或已发布协议需要迁移。后续破坏性修改必须新增 v2，不得静默修改 v1 的语义。生产数据库一旦应用迁移，不得修改已应用 SQL，应新增 V2、V3。

### 5.2 输入和回执规则

- GIFT 必须有独立 gift 输入及布局，SELLING_POINT 必须有至少一条非空人工卖点，SCENE 至少有场景模板或自定义描述。其他功能的专有字段拒绝；所有固定结构拒绝未知字段，不自动类型转换、不补写默认业务值。
- 输入引用使用非空 opaque ID；对象 key 为不含 URL、反斜杠、查询串、路径回退段的内部 ASCII 相对 key。哈希统一小写 64 位 SHA-256；图片二进制、永久 URL 和密钥不属于任务字段。
- 布局只定义 x/y 为 0..1、width/height 为正有限数，保留原稿比例表示；不确定裁切、旋转、真实比例或越界策略。语法通过不代表 D-02 已批准该变换。
- Worker 请求必须有原商品及 alpha 引用、模板/输出预设快照、输出前缀、event_id/task_id/attempt_id/correlation_id。赠品有独立引用，卖点仅传人工原文。快照中的 config 是版本化模板的透明配置载荷，此时不定义模板渲染语法，也不能直接当 AI 请求。
- 每个模板版本快照包含发布人、发布时间、版本及配置；自定义场景允许 versions 为空，输出预设仍需快照。场景模板描述与自定义描述可同时原样携带，本任务不执行拼接或生成。最终组合逻辑在 T09/模板规范中处理。
- 成功回执携带非空产物清单、ordinal、对象 key/哈希/尺寸、耗时，以及可空的 background_generation。使用 AI 背景时，该元数据必须含供应商、模型、提示词、生成参数、请求关联 ID、输出来源；这不是供应商选择。纯确定性产物填 null。
- 失败回执携带安全错误码、安全消息、retryable 和耗时。回执始终关联明确 attempt；对外 FAILED 响应只暴露安全错误，不公开供应商元数据。
- 日期时间必须带时区且为有效 date-time。QUEUED/RUNNING 响应无产物且 error=null；SUCCEEDED 至少一张产物且无错误；FAILED 无成功产物且有错误。实际状态推进、产物存在性校验、回执去重执行和旧 attempt 处理属于 T05。

### 5.3 数据库基线及幂等约束

PostgreSQL 是唯一业务数据库；由 Java 的 Flyway 管理迁移。Python 不装 PostgreSQL 驱动、不连接业务数据库。

V1 建立 users、projects、assets、templates、template_versions、generation_tasks、task_attempts、artifacts、outbox_events、worker_receipts、audit_events。ID 为 text，时间为 timestamptz，JSON 配置/快照为 jsonb。仅建立结构，不创建真实用户、管理员、素材、模板或供应商；users.role 不预设权限体系，等待 D-05/T04。

- 任务唯一键为 `(created_by, feature_type, idempotency_key)`，同时保存 `request_sha256` 与原始请求快照。相同用户/功能/key 无法插入第二个任务，即使哈希不同；不同用户或功能不互相占用 key。
- 幂等 SHA-256 由 Java 唯一计算：对象键排序、数字去除无意义尾零、数组顺序及字符串原文保留、UTF-8。拒绝重复 JSON 键、尾随 JSON 和不成对的 Unicode 代理字符，避免 UTF-8 替换产生指纹歧义。`1` 与 `1.0` 等价，不把不同文案或不同数组顺序当成相同输入。Python/浏览器不得另算一个不兼容的指纹。
- T03 验证唯一约束及并发冲突。相同 key/相同哈希返回既有任务、不同哈希返回 TASK_CONFLICT 的 HTTP 行为待 T05 在事务服务中实现，不能把唯一键异常直接当作成功。
- attempt 唯一 `(task_id, attempt_no)`；当前 attempt、产物、outbox 和回执通过复合外键绑定同一 task/attempt；产物唯一 `(attempt_id, ordinal)`，防止重试重复登记可见槽位。
- outbox 对同一 attempt 的请求事件唯一；worker_receipts 的 event_id 和 attempt_id 唯一，保存回执哈希供 T05 检查“重复事件却不同载荷”。这些表当前没有发布器/消费者。
- 任务商品引用必须指向 PRODUCT，赠品引用必须指向 GIFT；alpha 只能派生于原始 PRODUCT/GIFT，不能套用另一份 alpha。模板的发布指针必须指向已发布版本，PUBLISHED 状态必须有该指针；停用可保留历史发布版本。
- 源资产身份/来源、任务请求快照、已发布模板版本及产物记录不可覆盖；版本发布后不可更新或删除。更改产物应创建新 attempt/产物，保留旧记录。正式删除策略仍待 D-08，不实现自动删除。
- CHECK 校验状态、类型、正整数尺寸/序号、哈希、JSON 基本结构；复合外键防止任务引用另一项目资产、或引用另一个任务的 attempt。相应 FK 和轮询预期列建立索引，不引入 RLS/SSO 策略。

数据库能力仅在 `database` profile 显式启用，连接通过 DB_URL/DB_USER/DB_PASSWORD 注入；缺少配置必须启动失败。默认健康服务继续无数据库启动。无真实密钥的隔离验证使用 `scripts/check_db.py` 创建临时集群与一次性口令，日志和数据均在忽略目录。迁移默认禁用 clean/baseline-on-migrate；升级校验错误必须明确失败，不自动重建业务库。
