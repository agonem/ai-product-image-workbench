# 接口与数据契约草案 v0.1

业务接口仍是 **拟定契约**；T01 仅实现下述健康接口。路径与字段可在首次代码评审时调整，调整须同步 Schema、前后端和测试。所有资源 ID 为服务端生成的 opaque string；时间为带时区 ISO 8601；长度与业务上限待 P0 决定。

## 0. T01 开发环境健康接口

需求：PRD-G06；任务：T01；验收：ACC-T01。两个端点只反映当前 HTTP 进程可响应，不承诺数据库、Worker、AI 或业务就绪。

| 调用方 → 服务 | 方法与路径 | HTTP 200 JSON |
| --- | --- | --- |
| 前端 → Java | `GET /api/v1/health` | `{"status":"UP","service":"business-service","api_version":"v1"}` |
| 开发检查 → Python | `GET /internal/v1/health` | `{"status":"UP","service":"image-service","api_version":"v1"}` |

无输入、无密钥、无素材、无业务状态写入。前端通过 Vite 的 `/api` 开发代理访问 Java，不直连 Python。两服务默认仅绑定 `127.0.0.1`，没有实现认证，不能作为生产部署。前端在连接失败、超时或响应不符合上述字段时显示失败并允许重试。后续业务健康/就绪语义须单独定义；本次不改变任务 Schema。

## 1. 前端 → Java（/api/v1）

| 方法与路径 | 用途 | 要点 |
| --- | --- | --- |
| `POST /assets/uploads` | 获取受限上传凭证或走服务端上传 | project_id、type=PRODUCT/GIFT；回收未完成上传 |
| `POST /assets/{id}/complete` | 校验上传完成并处理元数据 | 校验 MIME 真值/文件大小/像素数/哈希/归属；返回可预览状态 |
| `POST /assets/{id}/cutout` | 发起或取得抠图结果 | alpha 预览与人工确认状态 |
| `GET /templates?type=scene|layout|style` | 已发布模板 | 返回版本、预览与允许参数 |
| `POST /tasks` | 创建独立生成任务 | 必须携带 `Idempotency-Key` 和 `feature_type`；返回 202 |
| `GET /tasks/{id}` | 轮询状态与结果 | 只返回当前授权用户可读的信息 |
| `POST /tasks/{id}/retry` | 针对失败任务重试 | 新 attempt，不能改写原配置快照 |
| `GET /artifacts/{id}/download` | 下载已授权结果 | 代理或短时效签名链接 |
| `POST /admin/templates` 等 | 草稿、测试、发布、停用 | 仅管理员；另行定义管理 API 细节 |

示例 `POST /tasks`：

```json
{
  "project_id": "p_123",
  "feature_type": "GIFT",
  "product_asset_id": "a_product",
  "gift_asset_id": "a_gift",
  "manual_text": "下单赠清洁刷",
  "template_version_id": "tv_layout_1",
  "layout": {"product": {"x": 0.12, "y": 0.11, "width": 0.72, "height": 0.72}, "gift": {"x": 0.70, "y": 0.72, "width": 0.22, "height": 0.22}},
  "output_preset_id": "preset_draft_1"
}
```

坐标是相对画布的 0..1 比例，原点左上；尺寸、旋转和允许越界范围要经 UI/图像引擎统一确认。赠品默认右下是界面初始值，可编辑；`output_preset_id` 在拼多多规格确认前只代表内部预览导出配置。

`SCENE` 专有字段：`scene_template_version_id` 或 `scene_custom_prompt`、可选 `style_custom_prompt`、商品布局；两种场景输入可以有明确组合规则，但不能都为空。`SELLING_POINT` 专有字段：`selling_points`（人工字符串数组）和 `layout_template_version_id`；一条文案一张产物，数量上限待定。三种类型使用 discriminated union 校验，绝不根据缺失字段猜类型。

统一任务响应：

```json
{
  "id": "t_123", "feature_type": "GIFT", "status": "QUEUED",
  "attempt": 1, "created_at": "2026-09-24T00:00:00Z",
  "artifacts": [], "error": null
}
```

失败响应示例：`{"code":"CUTOUT_REVIEW_REQUIRED","message":"请检查商品抠图边缘","correlation_id":"..."}`。最小错误码：`INVALID_ASSET`、`UNAUTHORIZED_ASSET`、`CUTOUT_REVIEW_REQUIRED`、`INVALID_LAYOUT`、`TEXT_OVERFLOW`、`PROVIDER_UNAVAILABLE`、`GENERATION_FAILED`、`OUTPUT_VALIDATION_FAILED`、`TASK_CONFLICT`。内部故障细节与供应商错误不得直接暴露。

## 2. Java → Python Worker

Java 在数据库事务中提交任务与 outbox 记录；发布器投递 `image.task.requested.v1`。Worker 只读取受限的对象引用/临时访问令牌，结果写到任务限定路径，回执 `image.task.completed.v1` 或 `image.task.failed.v1`。不得在消息体存放图片二进制、用户密码或长期密钥。初期若采用 DB 轮询，保留同一请求与回执语义。

请求契约草案见 `contracts/task.schema.json`，含 `schema_version`、`task_id`、`attempt_id`、`feature_type`、输入资产引用及哈希、模板快照和参数、目标路径、关联 ID。成功回执包含产物类型、对象引用、sha256、尺寸、耗时、供应商与模型标识；失败回执包含可重试标记、内部错误码和安全消息。Java 在更新状态前核验 attempt_id 与产物存在性，重复回执幂等处理；旧回执只记录不覆盖。

## 3. 表模型（概念级）

| 表 | 主键与关键字段 | 约束 |
| --- | --- | --- |
| `users` | id、role、status | 最小权限 |
| `projects` | id、owner_id、name | 项目归属 |
| `assets` | id、project_id、kind、object_key、sha256、width、height、review_status | 类型与访问权校验；源图不可被替换 |
| `templates` | id、type、name、published_version_id、state | 模板身份稳定 |
| `template_versions` | id、template_id、version、config_json、created_by、published_at | 一旦发布不可改写 |
| `generation_tasks` | id、project_id、feature_type、status、request_snapshot_json、created_by、created_at | type/状态受限；配置快照 |
| `task_attempts` | id、task_id、attempt_no、status、started_at、ended_at、error_code、provider_info | 唯一(task_id, attempt_no) |
| `artifacts` | id、task_id、attempt_id、kind、object_key、sha256、width、height | 成品不可悄然覆盖 |
| `outbox_events` | id、event_type、payload、published_at | 可恢复发布 |
| `audit_events` | id、actor_id、action、resource_id、timestamp | 记录敏感变更 |

用数据库迁移脚本实现；object_key 不应是公网永久地址。保存期限、清理孤儿产物和删除传播规则尚未决定。

## 4. 版本策略

对外 API `/api/v1`；任务 schema 有独立 `schema_version=1`；模板发布产生不可变版本；Prompt、供应商/模型和原图/alpha 哈希存任务快照。破坏性更改先引入新版本并让前端/Worker 双方通过契约测试，然后滚动发布。建议从契约生成 Java/Python/TypeScript 类型，但生成器是实现选项，不能取代人工审核语义。
