# T05 运行与恢复

需求 PRD-G03/G06、PRD-S01/S02/S03；验收 ACC-T05。此版本交付任务运输与持久化，不实现图像算法或正式登录。

## 启动

先按 07/09 安装锁定依赖及 PostgreSQL 17。默认三端健康服务继续使用 `python scripts/dev.py business|image|frontend`（分别执行）。只有显式设置 `SPRING_PROFILES_ACTIVE=runtime` 才开放任务路由；该 profile 包含 database 并执行 V1、V2 迁移。

在 Java 进程环境中设置 DB_URL、DB_USER、DB_PASSWORD、RUNTIME_USER_ID、RUNTIME_API_TOKEN、RUNTIME_WORKER_TOKEN、OBJECT_STORE_ROOT。两个 token 必须各至少 32 字符且不同，在本机生成并保存在仓库之外；没有默认凭据。用户必须已存在且 ACTIVE，项目必须归该用户所有。Java 仅允许绑定 127.0.0.1 或 ::1。本地 bearer 适配器不能代替 D-05 的正式认证决策。

Worker 的环境设置 WORKER_API_URL（如 http://127.0.0.1:8080）、RUNTIME_WORKER_TOKEN（与 Java 相同）、WORKER_JOURNAL_ROOT（私有持久目录），然后运行 `python scripts/dev.py worker`。Worker 只调 Java 内部 HTTP，不持有数据库账号。每个 Worker 使用独立 journal 目录；OS 文件锁防止同目录并发。Ctrl+C 可停止进程。

没有自动用户、素材、模板或输出预设种子。T04 尚未实现，正式上传/账号页面不可用。已有合法素材需包含源文件、正确摘要/尺寸、同项目且 APPROVED 的 ALPHA。模板必须有已发布版本；场景模板的 `config_json.prompt` 保存已审核提示词，Java 不将用户文字拼接成供应商提示词。输出预设由 output_presets 表提供，不是平台规则。

## 可复现验收

`python scripts/check.py` 运行静态检查、单元/契约测试及构建。`python scripts/smoke.py` 启动三个健康服务。`python scripts/check_db.py` 创建一次性本机 PostgreSQL 集群，测试迁移、启动 Java runtime 和独立 Python Worker，验证任务运输、崩溃及恢复，最后停止所有自己启动的进程。需配置 PG_BIN；合成素材、临时凭据、数据库和日志只留在忽略的 `.artifacts/`。

CI 可对明确的一次性 DB_TEST_URL/USER/PASSWORD 执行 `python scripts/check_t05.py`；先构建 Java jar、同步 Python 依赖，且 PATH 中需要 psql。脚本会创建随机 schema，不要将其指向生产数据库。测试自动生成 4×3 PNG，只有测试 Worker 的 `--fixture` 才原样搬运该素材；预设必须为 t05_transport_fixture，object key 必须以 fixtures/ 开头。此输出不能用作产品图或图像质量验收。普通 Worker 明确回报未实现/供应商不可用，不会伪装生成成功。

## 状态和故障恢复

Java 在一个事务写任务、attempt、outbox。相同幂等键和相同载荷返回原任务；不同载荷返回 409。Worker 通过 SKIP LOCKED 领取当前 attempt，心跳续租；进程中断后租约到期并经过退避才能再次领取。重复领取沿用不可变请求快照，租约 token 则更换。

Java 将图片原始字节写入私有文件系统，校验实际 PNG/JPEG 内容、尺寸、字节和像素预算。输出 PUT 使用 `application/octet-stream`。文件先落临时文件并 force，再用同文件系统硬链接原子发布；相同路径相同摘要可重放，不同字节拒绝覆盖。不支持硬链接的文件系统明确失败，不降级为覆盖。目录必须仅对服务账号可写；不承诺抵御同账号恶意并发修改目录。公开下载经过 Java 所有权鉴权，不返回存储路径。

Worker 先 fsync 本地 receipt journal 再发回执，确认后删除；重启先重放。Java 在事务内核验全部输出再写 artifacts 和终态；无文件/摘要错误不会成功。旧租约/旧 attempt 回执不能覆盖当前状态，同 event 重复回执返回相同确认，冲突回执 409。journal 的永久协议冲突保留现场并按退避重试，需运维核对该事件；不要通过删除业务记录掩盖问题。

开发默认租约 60 秒、最多交付 3 次、退避 2 秒、人工重试最多 5 次；可用 WORK_LEASE_SECONDS、WORK_MAX_DELIVERIES、WORK_BACKOFF_SECONDS、WORK_MAX_ATTEMPTS 配置。Worker 单次处理心跳最多持续 600 秒，超过后不确认产物，等待租约恢复。OBJECT_MAX_BYTES 默认 10 MiB、OBJECT_MAX_PIXELS 默认 1600 万；这些是技术保护值，不是图片规格或业务 SLA。耗尽交付次数转为可重试失败；重试创建新 attempt，不改历史结果。D-08 未定，孤立输出和 staging 文件保留，不自动删除。

## 版本与依据

沿用 T03 的 Java 21、Spring Boot、PostgreSQL 17.11、Flyway 和 JSON Schema 版本，不新增 Java 依赖。HTTPX 0.28.1 从已有开发依赖移至运行依赖，uv.lock 同步；在 Python 3.13.13 实际运行 Worker 验证兼容。前端依赖不变。

并发队列采用 PostgreSQL 官方说明的 [SKIP LOCKED](https://www.postgresql.org/docs/17/sql-select.html)，创建幂等使用 [ON CONFLICT](https://www.postgresql.org/docs/17/sql-insert.html)。重试先锁任务行，再以新语句读取 attempt，遵循 [READ COMMITTED 的语句快照](https://www.postgresql.org/docs/17/transaction-iso.html)。文件发布避免依赖 [Files.move 的目标覆盖语义](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/Files.html)。HTTPX 配置明确的 [超时](https://www.python-httpx.org/advanced/timeouts/)，应用层通过租约/幂等回执承担重放语义。
